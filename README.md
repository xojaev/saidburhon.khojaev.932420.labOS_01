## 1. Постановка задачи
Реализовать монитор, обеспечивающий безопасный и эффективный обмен событиями
между двумя потоками:
- поток-поставщик раз в секунду инициирует условное событие и сообщает об этом;
- поток-потребитель принимает событие и сообщает об обработке.

Требования:
- сообщения не должны нарушать очерёдность (сначала «отправлено», затем «обработано»);
- ожидание события не должно нагружать процессор (никакого активного ожидания);
- событие может содержать несериализуемые данные (передаётся по указателю);
- корректное завершение потоков без «вечного» ожидания.

## 2. Что такое монитор в данной работе
Монитор объединяет четыре элемента:
1. формальный критерий наступления события — флаг `ready`;
2. разделяемые данные — указатель `event` на `Event` (внутри — `Payload`);
3. инструмент блокировки доступа — `pthread_mutex_t mutex`;
4. механизм ожидания уведомления — `pthread_cond_t condition`.

Монитор имеет смысл только при нескольких потоках: один поставщик и один
потребитель (в общем случае их может быть больше).

## 4. Как работает синхронизация
### Поставщик (`Monitor::provide`)
1. Захватывает мьютекс.
2. Пока предыдущее событие не обработано (`ready == true`) и монитор не
   остановлен — ждёт на условной переменной.
3. Кладёт указатель на новое событие, ставит `ready = true`.
4. Печатает сообщение «отправил событие N».
5. Будит потребителя (`pthread_cond_signal`).
6. Отпускает мьютекс.

### Потребитель (`Monitor::consume`)
1. Захватывает мьютекс.
2. Пока события нет и монитор не остановлен — ждёт:
   `while (!ready && !stopped) pthread_cond_wait(&condition, &mutex);`
3. Если проснулся из-за остановки — выходит, вернув `false`.
4. Иначе печатает «обработал событие N, данные V», освобождает `Payload` и
   `Event`, сбрасывает `ready = false`.
5. Будит поставщика (если он ждёт освобождения слота).
6. Отпускает мьютекс, возвращает `true`.

### Завершение (`Monitor::stop`)
Поставщик после последнего события вызывает `stop()`:
- под мьютексом ставит `stopped = true`;
- вызывает `pthread_cond_broadcast`, чтобы разбудить всех ожидающих;
- отпускает мьютекс.

Потребитель просыпается, видит `ready == false` и `stopped == true`,
завершает цикл `while (consume())`.

## 5. Ключевые решения и почему они правильные
- **Ожидание в цикле `while`, а не `if`.** Защищает от ложных пробуждений и от
  сигнала, пришедшего до вызова `wait`. Поток после пробуждения всегда
  перепроверяет условие.
- **`pthread_cond_wait` временно освобождает мьютекс.** Поэтому поставщик может
  войти в монитор, пока потребитель спит, — иначе был бы тупик. Ожидание при
  этом не расходует процессор (в отличие от `while (!ready) {}`).
- **Все обращения к `ready`, `stopped`, `event` — только под мьютексом.**
  Это исключает гонку данных.
- **Запрет копирования монитора** (`= delete` для конструктора копирования и
  оператора присваивания): копия мьютекса — это два разных замка на одни
  данные, то есть сломанная синхронизация.
- **Передача несериализуемых данных по указателю.** `Event` содержит
  `Payload*`; владение передаётся потребителю, который освобождает память
  ровно один раз.
- **Корректное завершение через `stopped` + `broadcast`.** Ни один поток не
  остаётся спать вечно; при остановке даже непринятое событие освобождается.
